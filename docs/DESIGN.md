# Relative Ear：Android 相对音感训练设计

文档版本：0.5（应用版本独立采用 0.0.x）
日期：2026-10-07  
状态：基础实现已开始；以下性能与识别指标为验收目标，不是已测结果。实际完成范围和与设计的差异见 [DEVELOPMENT.md](DEVELOPMENT.md)，验证边界见 [TESTING.md](TESTING.md)，发布流程见 [RELEASE.md](RELEASE.md)。

## 1. 产品目标

帮助音乐爱好者形成“听到声音能认出 Do / Re / Mi，并能唱出来”的能力，而不要求先掌握音程术语。当前按用户确认采用固定唱名，以 C4 为 Do，默认 A4=440 Hz，C4 约 261.63 Hz；不再随机移调。

产品必须提供三种互补能力，按以下阶段实现：

1. **练耳**：辨认固定音高；默认 C4/D4/E4，提供三音、五音、八音与自选范围，答案可用唱名或音名。
2. **唱唱名**：给定 C4 基准与目标唱名/音名，用户唱出目标，自动反馈音高和稳定性。
3. **识别周围音乐**：实时监听，识别人声或乐器连续单音旋律，显示音符序列、频率、音分偏差及音高曲线；带伴奏音乐的主旋律提取列入独立技术验证阶段。

产品差异点是“试听记忆 → 短音判断 → 唱 → 客观反馈”的闭环，以及面向初学者的小范围快速训练。

## 2. 范围与非目标

### 2.1 MVP 范围

| 模块 | 首版能力 |
|---|---|
| 练耳 | C4–C5 自然音，可选三音、五音、八音或自选；每题一个短音，答案以 MIDI 音高作为身份，不因显示形式改变 |
| 示范与反馈 | 音符记忆台可单独试听，示范实时对应音名/唱名/谱位；答后听答案，答前不显示真实谱位 |
| 唱唱名 | C4 + 指定音符；自动音准评分；未保存八度设置时默认区分八度，保留已有用户选项 |
| 识别周围音乐 | 实时单音音名、八度、Hz、cents、置信状态、最近约 10 秒曲线；连续单音旋律的音符分段、起始时间和持续时间 |
| 训练记录 | 按模式、音程或级数统计首次回答正确率、反应时间、回唱误差和错题 |
| 设置 | 音域、音量、A4 基准、音准容差、主题、数据删除 |
| 检查更新 | 用户主动查询公开 Releases，包含预览版；数值版本与完整官方资产校验、按 ABI 提示下载安装包 |

初学者默认 C4/D4/E4，熟悉后扩展至 C4–G4 五音、C4–C5 八音。自选集合可不连续，至少保留一音。范围、答案显示、速度持久化，整轮锁定；固定 C4 不跨轮改变。旧版音程与首调仅保留历史和领域兼容逻辑，不再作为主训练 UI。

八分音符按四分音符为一拍的半拍时值实现，支持 60/80/100/120 BPM，每音槽 `30000/BPM` 毫秒，其中约 85% 发声、15% 静音断奏。音符与间隔在同一 PCM 时间轴，不使用协程逐音延迟拼接。当前不做节奏正确率或完整旋律评分。

### 2.2 明确不做

更新入口不在启动或后台自动联网，不自动下载/安装 APK。查询失败不伪装成最新版本；下载交给外部应用，覆盖安装沿用固定签名。训练依旧离线，联网边界见 [PRIVACY](PRIVACY.md)。

- 首个可用版本不承诺带伴奏歌曲主旋律提取；该能力属于产品后续技术验证范围，不以单音检测冒充完成。
- 和弦全声部转录、歌曲完整转谱、自动识别完整歌曲调性。
- 对所有环境声音强制给出音符。噪声、打击声或多声源可以没有可信单一音高。
- 账号、云同步、社交、排行榜、订阅和后台常驻监听。
- 完整视唱谱面、旋律节奏评分、专业音乐能力认证。

识音页面必须明确提示当前模式“适用于单音旋律；带伴奏音乐可能无法识别”。不可将低置信结果包装为确定音符，也不把“音乐识别”宣传为歌曲名称检索。

### 2.3 已确认的项目约束

- 仓库：`gongpx20069/relative-ear`，公开；使用 GitHub REST API 创建和管理远端资源。
- 应用版本：仅使用 `0.0.x`，首个版本为 `0.0.1`。
- APK 发布：由 GitHub Actions 构建，发布到 GitHub Releases。
- 平台：一般 Android 手机，最低 Android 8.0（API 26），不依赖特定厂商硬件。
- 三个首页入口都必须实现，不删除识音功能以缩减为纯练耳 App。
- 无指定机型不阻塞开发，但真实音频精度和性能仍需真机验证。

## 3. 核心交互

### 3.1 页面

- **首页**：听辨、回唱、实时识音、最近训练。
- **训练配置**：模式、题目集合、方向、题数、音域及难度。
- **训练页**：播放、重播、回答、解释、下一题。
- **识音页**：当前音、偏差指示、历史曲线、开始/停止监听。
- **报告页**：正确率、易错项、回唱误差、推荐练习。
- **设置页**：声音、评分、隐私、第三方声明。

颜色不是唯一反馈方式，正确/错误同时使用文字或图标；文本支持系统字体缩放。

视觉采用奶白背景、松绿主色、薄荷辅助与金色音符，圆角卡片分组；默认折叠配置，中心练习卡与主操作优先。底栏使用绘制图标，不再用文字首字冒充图标。答前只展示无谱位的装饰性八分音符；示范、回唱目标与答后才展示真实高音谱表位置。实时识音使用音准指示条与曲线，历史显示配置快照；所有页面共享主题和间距。

### 3.2 听辨

1. 生成一组满足音域与题型约束的题目。
2. 播放选中范围内的单个八分音符；基准与示范供用户在开练前试听。
3. 播放结束后开放回答；反应时间从此刻开始计算。
4. 首次提交后显示正确答案和解释，允许复听。
5. 每轮默认 10 题，结束后生成报告。

练习模式允许重播；记录重播次数。测试模式单独配置，不提供答题前提示，并将测试与练习结果分开统计。

### 3.3 回唱

例：播放 C4 → 显示 Mi / E4 → 用户唱出 E4 → 显示目标偏差与判定。

流程：

1. 播放 C4 基准，停止播放。
2. 等待可配置的回声保护时间，默认 250 ms；该值需要真机验证。
3. 显示“请唱”，开启评分窗口；优先建议使用有线耳机。
4. 检测到可信、稳定的音高片段后评分。
5. 默认窗口为 8 秒；无可信声音、声音不稳定、音准错误分别显示不同反馈。
6. 用户可重试，但保留首次有效结果，不覆盖历史成绩。

不在扬声器播放题目时同时评分。蓝牙耳机的路由、延迟和麦克风质量差异较大，不保证首版评分体验。

### 3.4 实时识音

用户主动开始监听。稳定声音显示如 `A4 · 440 Hz · -7 cents`；低音量或低置信时显示“未检测到稳定单音”，清除当前音，不保留看似有效的旧读数。

这里的音分偏差针对最近音符；回唱页的音分偏差针对目标音，两者不可混用。

连续识音将稳定片段转成 `C4 → E4 → G4` 这样的序列，每个音包含起始时间、持续时间和置信度。指定调性后才能显示调内级数；未指定时只显示音名。

音符分段结合音高变化、静音间隔和起音证据；不能只对 MIDI 音号去重，否则会吞掉连续重复的同音。使用滞回及最小持续时间过滤颤音和边界抖动，参数经测试集调整。当前音符先以临时状态显示，结束后再确定持续时间。

带伴奏主旋律识别如后续接入模型，必须作为独立模式，有明确设备要求和能力说明，不能静默回退到单音检测而声称识别成功。

## 4. 训练与评分规则

### 4.1 相对音感不是绝对音感

当前固定唱名题使用 C4 参照，示范供用户建立声音记忆，不自动换调；听辨只播放目标音。识音模式仍显示绝对音名，不尝试把未知歌曲的 C 自动解释为歌曲的 Do。固定音高记忆不等于掌握任意调性的首调能力。

旧级数领域逻辑按已知调性计算；不尝试从任意环境单音推断调性。当前固定音符的答案与实际播放使用同一个不可变题目对象。

### 4.2 音高换算

```text
fractionalMidi = 69 + 12 × log2(frequency / referenceA4)
nearestMidi   = round(fractionalMidi)
noteCents     = 100 × (fractionalMidi - nearestMidi)
targetCents   = 100 × (fractionalMidi - targetMidi)
```

`referenceA4` 默认为 440 Hz，设置允许 415–466 Hz；播放与检测必须共用同一基准。

严格八度模式使用完整 MIDI 音高；忽略八度模式显式将目标误差折算到最接近的八度等价音，报告标记该模式。

### 4.3 回唱初始参数

以下参数均集中配置，后续依据真机录音和用户试验调整：

- 检测音域初始为 65–1000 Hz，超出范围显示提示，不判成错误音。
- 使用检测器置信度门限和音量门限，拒绝静音、噪声及不可靠帧。
- 最小稳定片段为 400 ms，按时间戳计算，不能简单用重叠帧数相加。
- 片段中至少 80% 的时间有可信音高；片段误差使用中位数。
- 默认正确容差为 ±35 cents，并允许配置 ±20、±35、±50 cents。
- 稳定性初始阈值为片段音高的中位绝对偏差不超过 20 cents。
- 正确需同时满足稳定性与目标误差；可信但不稳定时提示“再稳一些”，不是直接判错。

使用首次达到稳定条件的片段判定，不能从整个录音里事后挑选最接近答案的一小段。连续反馈与最终评分分离，平滑后的 UI 曲线不能替代原始有效检测数据。

不得利用已知目标音把检测结果强制吸附到正确答案。八度跳变处理只依据声音与连续性；无法确定时降低置信度。

### 4.4 统计口径

- 听辨正确率 = 首次回答正确数 / 已回答题数。
- 回唱正确率 = 正确题数 / 已完成评分窗口数，包含超时题。
- 无可信输入单列，帮助区分设备或环境问题；取消或音频故障题不计分。
- 反应时间记录重播影响；回唱误差只统计有可信片段的题，不能把超时写成 0 cents。
- 根据当前模式最近 100 道有效题的错误率推荐弱项；样本不足时明确提示。
- 自适应练习加入均匀随机题，避免长期只练少数错题。

## 5. 技术架构

### 5.1 首选栈

| 层 | 方案 |
|---|---|
| UI | Kotlin、Jetpack Compose、Material 3 |
| 状态 | ViewModel、StateFlow、协程 |
| 音频采集 | AudioRecord，独立工作线程 |
| 音频播放 | AudioTrack + 本地合成音；首版不依赖未核实授权的钢琴采样 |
| 检测 | 独立纯 Kotlin YIN 实现，先测性能再决定是否引入原生代码 |
| 持久化 | Room 保存训练；DataStore 保存偏好 |
| 测试 | JVM 单元测试、Android 仪器测试、真机录音回放 |
| 平台 | minSdk 26（Android 8.0）；targetSdk 使用实施时符合发布要求的版本 |

优先独立开发而非 fork OpenEar：原生实时音频集成更直接，避免 Angular、WebView、插件与原生模块混合调试。

若实测 AudioRecord 无法达成延迟或稳定性目标，再考虑 Oboe + C++ 检测；不是第一版的前置依赖。

### 5.2 模块边界

```text
:app             页面、导航、依赖装配
:core:music      音名、音程、音阶、题目生成
:core:audio      采集、播放、设备路由、检测接口
:core:training   状态机、有效片段判定、评分、推荐
:core:data       Room、DataStore、数据迁移
```

音乐理论和评分计算尽量使用纯 Kotlin，不依赖 Android，便于确定性测试。

音频接口应返回带时间戳的 `PitchFrame`：频率、置信度、音量、有效状态。不用 `0 Hz` 或 `NaN` 伪装“无结果”。

### 5.3 状态机

```text
Idle → Preparing → Playing → Settling → Listening
     → Evaluating → Feedback → Completed / Preparing
```

听辨题从 Playing 进入 AwaitingAnswer；只有麦克风训练才进入 Listening。

任意活动状态可进入 Interrupted 或 Error。播放和识音共享唯一音频会话控制器，避免多页面同时占用麦克风。启动失败、路由中断、权限拒绝必须有明确 UI，不写入假成绩。

### 5.4 数据模型

- `TrainingSession`：模式、训练/测试标记、配置快照、评分版本、开始/结束时间。
- `QuestionAttempt`：题目、基准和目标、首次答案、重播/重试次数、结果原因、反应时间、可选误差和稳定性。
- `TrainingSettings`：音域、A4 基准、容差、方向与题型集合。
- `RecognizedNoteEvent`：音高、起始时间、持续时间、置信度与临时/已结束状态；首版识音序列只在内存中保留。

不持久化逐帧音频或 PCM。曲线使用内存环形缓冲区；默认只保存结果摘要。未来如增加录音，必须另行设计用户同意、保存期限与删除能力。

## 6. 音频处理设计

```text
麦克风 PCM → DC 去除 / 必要滤波 → 音量门限
           → YIN → 音域和置信检查
           → 连续性检查 → 稳定片段 → 评分 / 音符分段 / UI
```

- 使用设备支持的采样率，初始优先尝试 48 kHz 单声道，并核实实际配置。
- 初始分析窗 4096 样本、步长 512 样本；在 48 kHz 下约为 85 ms 窗与 11 ms 步长。
- 低音需要更长窗口，延迟与音域存在取舍；不保证所有音域同样快。
- 不在实时路径逐帧分配大对象，不在主线程处理 PCM；采样积压时跳过旧分析帧，并记录诊断计数。
- UI 更新约 20–30 Hz，不随每个采样块重绘。
- 滤波不得破坏目标低音基频；不默认叠加重度降噪或自动增益。
- YIN 直接实现可能耗时较高，必须在目标机上 profiling；优化或降采样须验证识别指标没有退化。
- 启动时可以测量环境底噪，但持续有声音时不能假装完成校准；允许重试或采用显式默认门限并提示。

诊断日志仅含设备配置、耗时与错误码，不含原始音频。涉及库的置信度定义时，必须适配和测试，不假设不同检测器的数值可直接比较。

## 7. 权限、生命周期与隐私

- 仅在用户启动识音或回唱时请求 `RECORD_AUDIO`。
- 纯听辨模式不要求麦克风授权；拒绝授权后仍可使用。
- 默认本地处理，不上传音频，不使用后台服务持续监听。
- 页面离开、应用进入后台、音频中断时停止采集并释放资源。
- 回到前台需要用户重新开始；受中断题目不自动提交。
- 来电、耳机拔出、音频路由变化和权限撤销需覆盖。
- 提供一键删除本地训练数据；首版不自动将数据库纳入系统云备份。

## 8. 验证与验收

### 8.1 算法与领域测试

- A4 换算、不同调音基准、跨八度、音程方向和调内级数映射。
- 每种配置生成的题目均在音域内；无可用组合时提示配置错误。
- 合成正弦波、带泛音波形、人声与乐器授权测试录音。
- 静音、白噪声、短促打击、双音和八度跳变。
- 评分容差边界、稳定时长、重叠窗口、超时、取消、首次回答统计。
- 连续旋律分段：换音、重复同音、连奏、断奏、滑音、颤音与静音；统计音符识别正确率、遗漏/插入数量和起止时间偏差。

### 8.2 初始验收目标

| 项目 | 目标与测量口径 |
|---|---|
| 干净单音精度 | 65–1000 Hz 合成测试集，至少 95% 的有效稳定帧绝对误差 ≤10 cents；同时报告有效帧覆盖率，避免靠拒绝结果获得高精度 |
| 真实录音精度 | 固定标注的人声与单音乐器测试集，稳定区间至少 90% 的分析帧有效且绝对误差 ≤25 cents；单独报告八度错误率 |
| 静音误报 | 60 秒静音中，无触发“稳定音”判定 |
| 噪声拒绝 | 固定白噪声与无调性打击测试集，至少 95% 的 1 秒窗口不产生稳定音判定 |
| 显示延迟 | 前台连续识音，受支持音域内稳定单音起始至首次有效 UI 显示的 P95 ≤250 ms；真机实测，不以帧步长替代端到端延迟 |
| 稳定性 | 30 分钟识音无崩溃、无持续积压，结束后音频资源释放 |
| 离线能力 | 飞行模式下完整完成三类训练并保存报告 |
| 权限退化 | 拒绝麦克风后，听辨功能正常；识音入口明确解释缺失权限 |

先固定测试集、标注方法和至少三款不同厂商真机，再评估目标是否达成。单音检测器可能把双音识为某个基频，不能承诺自动排除所有复音。

### 8.3 用户验证

邀请音乐初学者和有经验用户验证：能否通过示范建立 Do 的感觉、听辨并唱出唱名；评分是否公平；反馈是否帮助纠正，而不是只显示分数。

训练分数只是当前配置下的表现，不包装成通用“相对音感等级”或专业测评结论。

## 9. 实施顺序

1. **工程与发布基础**：Android 工程、单元测试基础、版本配置、GitHub Actions 与首个可安装 APK。
2. **技术验证**：音频采集、YIN、实时单音显示、连续旋律分段、固定测试集与真机测量。
3. **核心闭环**：生成题目、播放基准、回唱状态机、自动评分与中断处理。
4. **训练产品**：固定 C4 唱名听辨与回唱、三/五/八音及自选范围、八分音符快速播放、精简练习台、记录与报告。
5. **发布准备**：权限与隐私文案、无障碍、第三方许可和机型验证。
6. **复杂音乐验证**：评估端侧主旋律提取模型的授权、准确率、延迟、内存和不同 Android 设备表现；未达标时明确报告，不伪称支持。

先验证音频，不先投入完整 UI 或课程。若真实录音检测达不到要求，先修检测和有效片段判断，不用扩大评分容差掩盖问题。

工作量取决于经验、设备覆盖和测试结果；此前“约一周原型、1–2 个月 MVP”仅为粗略估计，不是交付承诺。

## 10. 版本与 GitHub Actions 发布设计

### 10.1 版本规则

- 在工程内集中保存应用版本，`versionName = 0.0.x`，`versionCode = x`，x 为正整数。
- Git 标签采用 `v0.0.x`，例如 `v0.0.1`；发布工作流校验标签与工程版本完全一致。
- 发布构建只能接受 `^v0\.0\.[1-9][0-9]*$`，并检查 `versionCode` 为 Android 支持的整数范围。
- 版本只递增，不覆盖已发布标签，不以工作流运行次数产生隐式版本。

### 10.2 CI 与发布链路

工作流已随 Android 工程加入；远端运行仍需认证和签名配置，详见 [RELEASE.md](RELEASE.md)。

- PR 和 main 推送：运行 JVM 测试、Android lint、APK 构建，不创建 Release。
- 推送 `v0.0.*` 标签：严格校验标签格式及版本，检查该提交已进入 main，运行测试与 lint，构建签名 release APK。
- 普通 CI 仅授予 `contents: read`；发布任务授予 `contents: write`，使用仓库作用域的 `GITHUB_TOKEN`，不使用个人长期 token。
- 通过 REST API `POST /repos/{owner}/{repo}/releases` 创建 draft Release。
- 通过返回的上传地址上传 `relative-ear-0.0.x-<architecture>.apk` 的四种 ABI 包、通用包与合并 `SHA256SUMS.txt`；六项资产全部上传并确认后，再使用 REST API 将 draft 发布。
- 构建、校验或上传失败不得发布完整 Release；失败必须使工作流退出非零。
- 重试仅允许处理当前标签的 draft；已公开发布的版本不覆盖，使用新版本。
- 同一标签的发布任务使用 concurrency 防止重复并行发布，执行中不自动取消。
- Release 说明列出功能状态、已知限制、最低 Android 版本和安装方式；早期 `0.0.x` 标记为 prerelease。

### 10.3 APK 签名

- 所有 release 版本使用固定应用 ID 和同一签名密钥，确保用户可以覆盖升级并保留数据。
- 签名材料和密码只放 GitHub Actions Secrets，临时文件在任务结束时清理；密钥需由管理员离线备份。
- Secrets 缺失时发布失败，不能生成新临时密钥或把 debug APK 当作正式升级包。
- APK 发布前执行签名、版本、原生库 ABI 与完整产物集合验证，并确认五个 APK 使用同一证书；不只检查文件存在。
- minSdk 26，独立构建 arm64-v8a、armeabi-v7a、x86_64、x86 和 universal APK；共享版本号，每个包可独立安装。
- 公开仓库不包含签名密钥、token、个人录音或未授权测试音乐。
